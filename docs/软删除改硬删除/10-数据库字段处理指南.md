# 数据库字段处理指南

## 概述

本次修改的核心是将代码中的软删除逻辑改为硬删除，但对于数据库中的 `is_deleted` 字段，建议采用分阶段处理策略。

---

## 处理策略

### 阶段一：代码层修改（本次进行）

**目标**：修改所有Java代码，将软删除改为硬删除，但保留数据库字段。

**操作**：
1. ✅ 修改Repository查询方法，删除 `isDeleted = false` 条件
2. ✅ 修改Service删除方法，将 `setIsDeleted(true)` 改为 `delete()`
3. ✅ 保留数据库中的 `is_deleted` 字段

**原因**：
- 降低风险：如果代码修改有问题，可以回滚
- 数据安全：保留历史数据标记，便于问题排查

---

### 阶段二：验证期（代码修改后1-2周）

**目标**：验证硬删除功能正常工作。

**验证内容**：
1. ✅ 所有删除操作都执行物理删除
2. ✅ 查询结果不包含已删除数据（因为已物理删除）
3. ✅ 删除后可以重新添加相同标识的数据
4. ✅ 系统运行稳定，无异常

---

### 阶段三：数据库清理（验证通过后）

**目标**：清理数据库中 `is_deleted = true` 的数据，并考虑删除字段。

#### 步骤1：清理已软删除的数据

```sql
-- 在执行此操作前，请确保已备份数据库

-- 查看各表中已软删除的数据量
SELECT 'tb_bankrupt_case' as table_name, COUNT(*) as deleted_count 
FROM tb_bankrupt_case WHERE is_deleted = 1
UNION ALL
SELECT 'tb_case_task', COUNT(*) FROM tb_case_task WHERE is_deleted = 1
UNION ALL
SELECT 'tb_creditor_claim', COUNT(*) FROM tb_creditor_claim WHERE is_deleted = 1
-- ... 其他表
;

-- 物理删除已标记为删除的数据（谨慎操作！）
-- DELETE FROM tb_bankrupt_case WHERE is_deleted = 1;
-- DELETE FROM tb_case_task WHERE is_deleted = 1;
-- ... 其他表
```

#### 步骤2：删除 is_deleted 字段（可选）

**注意**：此步骤风险较高，建议在系统稳定运行一段时间后再执行。

```sql
-- 删除 is_deleted 字段（谨慎操作！）
-- ALTER TABLE tb_bankrupt_case DROP COLUMN is_deleted;
-- ALTER TABLE tb_case_task DROP COLUMN is_deleted;
-- ... 其他表
```

**建议**：可以保留 `is_deleted` 字段，将其作为备用字段，或改名为 `deleted_flag` 标记为废弃。

## 注意事项

1. **备份优先**：执行任何清理操作前，务必备份数据库。

2. **逐步执行**：建议分批次执行清理脚本，每次清理一个模块的数据，观察系统反应。

3. **保留审计日志**：`tb_audit_log` 表建议保留，不清理已删除数据，用于审计追踪。

4. **监控磁盘空间**：清理大量数据后，可能需要执行 `OPTIMIZE TABLE` 释放磁盘空间。

5. **外键约束**：如果表之间有外键约束，需要按正确的顺序删除数据（先子表后父表）。

1. **添加删除日志表**：记录谁删除了什么数据，用于审计：
```sql
CREATE TABLE tb_delete_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    table_name VARCHAR(100) NOT NULL,
    record_id BIGINT NOT NULL,
    record_data JSON,
    deleted_by BIGINT,
    deleted_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    reason VARCHAR(500)
);
```

3. **数据保留策略**：制定数据保留策略，例如案件结案后N年自动归档或删除。
