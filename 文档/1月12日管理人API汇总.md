## 1. API接口概述

### 1.1 用途说明

管理人信息管理API提供了破产案件中管理人及其员工信息的完整管理功能，包括：

- **管理人信息管理**：创建、查询、更新、删除管理人（律师事务所、会计师事务所等机构）信息
- **管理人员工管理**：管理管理人机构下的员工信息，支持员工与系统用户账号的关联
- **数据关联**：管理人信息与破产案件、系统用户等模块的数据关联

### 1.2 适用场景

- **案件管理人指定**：在破产案件流程中指定管理人机构
- **管理人团队管理**：管理管理人机构的工作人员信息
- **员工账号关联**：将员工信息与系统登录账号进行关联，实现权限管理
- **信息维护**：对管理人及员工信息进行日常维护和更新

### 1.3 业务规则

1. 每个破产案件可以关联多个管理人
2. 每个管理人可以管理多个员工
3. 员工可以关联系统用户账号，用于登录和权限控制
4. 管理人名称为必填项，不能为空
5. 删除操作采用物理删除，请谨慎使用

## 2. 接口列表

### 2.1 管理人信息管理模块

| 序号 | 接口名称 | 请求URL | 请求方法 | 功能描述 |
|------|----------|---------|----------|----------|
| 1 | 创建管理人信息 | `/administrator` | POST | 创建新的管理人信息 |
| 2 | 管理人列表 | `/administrator/list` | GET | 查询管理人列表（支持分页和筛选） |
| 3 | 获取管理人详情 | `/administrator/{administratorId}` | GET | 根据ID获取管理人详细信息 |
| 4 | 更新管理人信息 | `/administrator/{administratorId}` | PUT | 更新管理人信息 |
| 5 | 删除管理人信息 | `/administrator/{administratorId}` | DELETE | 删除管理人信息 |

### 2.2 管理人员工管理模块

| 序号 | 接口名称 | 请求URL | 请求方法 | 功能描述 |
|------|----------|---------|----------|----------|
| 6 | 添加管理人员工 | `/administrator/{administratorId}/staff` | POST | 为管理人添加员工 |
| 7 | 员工列表 | `/administrator/{administratorId}/staff/list` | GET | 查询指定管理人的员工列表 |
| 8 | 获取员工详情 | `/administrator/{administratorId}/staff/{staffId}` | GET | 获取员工详细信息 |
| 9 | 更新管理人员工信息 | `/administrator/{administratorId}/staff/{staffId}` | PUT | 更新员工信息 |
| 10 | 删除管理人员工信息 | `/administrator/{administratorId}/staff/{staffId}` | DELETE | 删除员工信息 |

### 2.3 请求头要求

所有接口均需包含以下请求头：

| 请求头名称 | 值 | 说明 |
|------------|-----|------|
| Content-Type | `application/json` | 请求体为JSON格式 |
| Authorization | `Bearer {token}` | 认证令牌（待实现） |

## 4. 响应数据结构

### 4.1 通用响应格式

所有接口的响应均采用统一的JSON格式：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

### 4.2 响应字段说明

| 字段名称 | 数据类型 | 描述 |
|----------|----------|------|
| code | Integer | 状态码，200表示成功，其他值表示失败 |
| message | String | 响应消息，成功时为"success"，失败时为错误信息 |
| data | Object/String/Array/Null | 响应数据，具体结构根据接口而定 |

### 4.3 状态码说明

| 状态码 | 说明 | 示例消息 |
|--------|------|----------|
| 200 | 请求成功 | "success" |
| 400 | 请求参数错误 | "参数验证失败" |
| 404 | 资源不存在 | "管理人信息不存在" |

## 6. 注意事项

### 6.1 权限要求

1. **认证机制**：当前版本使用模拟用户ID（固定为1L），实际部署时需要集成JWT认证
2. **权限控制**：建议根据用户角色设置不同的操作权限
   - 普通用户：仅可查看信息
   - 管理员：可进行创建、更新、删除操作
3. **数据隔离**：用户只能访问自己有权限的案件和管理人信息

### 6.2 数据格式限制

1. **字符串长度限制**：
   - 管理人名称：不超过200字符
   - 管理人类型：不超过50字符
   - 联系电话：不超过50字符
   - 联系邮箱：不超过100字符
   - 办公地址：不超过500字符
   - 员工姓名：不超过100字符
   - 人员类型：不超过50字符
   - 身份证号：不超过50字符
   - 律师执业证号：不超过50字符
   - 职责描述：不超过255字符

2. **日期格式**：
   - 日期字段使用ISO 8601格式：`YYYY-MM-DD`
   - 时间戳字段使用ISO 8601格式：`YYYY-MM-DDTHH:mm:ss`

3. **必填字段**：
   - 创建管理人时：`administratorName`、`caseId`、`administratorType` 为必填
   - 创建员工时：`administratorId`、`name`、`staffType` 为必填

### 6.3 特殊业务逻辑说明

1. **外键关联**：
   - `caseId` 必须关联到有效的破产案件（`tb_bankrupt_case`表）
   - `responsiblePersonId` 必须关联到有效的员工（`tb_administrator_staff`表）
   - `userId` 必须关联到有效的用户（`tb_user`表）

2. **级联删除**：
   - 删除案件时，关联的管理人信息会被设置为NULL
   - 删除员工时，关联的用户信息会被设置为NULL
   - 删除用户时，关联的员工信息会被设置为NULL

3. **更新操作**：
   - 更新操作支持部分字段更新，只更新请求中包含的非空字段
   - `caseId` 和 `administratorType` 不支持更新（如需修改，请删除后重新创建）

4. **删除操作**：
   - 当前版本采用物理删除，删除后数据无法恢复
   - 建议在生产环境中使用软删除（通过 `isDeleted` 字段标记）

### 6.4 错误处理

1. **参数验证错误**：
   - 必填字段为空时返回400错误
   - 字段长度超限时返回400错误
   - 数据格式不正确时返回400错误

2. **业务逻辑错误**：
   - 案件不存在时返回404错误
   - 员工不存在时返回404错误
   - 用户不存在时返回404错误
   - 管理人不存在时返回404错误

3. **系统错误**：
   - 数据库连接失败时返回500错误
   - 服务器内部异常时返回500错误

### 6.5 性能优化建议

1. **分页查询**：
   - 列表查询建议使用分页，避免一次性加载大量数据
   - 默认每页大小为10，可根据实际需求调整

2. **索引使用**：
   - 数据库已为常用查询字段建立索引
   - 建议在查询时使用索引字段进行筛选

3. **缓存策略**：
   - 对于不常变动的数据（如管理人类型列表），建议使用缓存
   - 缓存失效时间建议设置为5-10分钟

### 6.6 测试建议

1. **单元测试**：
   - 已提供完整的单元测试用例
   - 测试覆盖了正常场景和异常场景

2. **集成测试**：
   - 建议使用Postman或类似工具进行接口测试
   - 测试时注意检查响应状态码和数据格式

3. **压力测试**：
